Open Blueprint for Cloud-Native AI Agents

Architecture reference for operating autonomous agents as governed cloud-native workloads. Three views — full blueprint, security deep dive, and inference routing — each backed by open interfaces.

Solution Architecture

Three horizontal bands — control, execution, platform — with the MCP Gateway as the checkpoint between them. Every component is a role that several implementations can fill; the architecture stands on open interfaces.

Control band

Creates and governs agents. An agent blueprint declares what each agent is made of; the sandbox control plane turns it into a resource; a controller turns it into one pod; identity issues every pod a verifiable credential.

Agent pod

One pod per sandbox. The harness owns the loop. The supervisor (OpenShell, PID 1) enforces per-binary network policy, Landlock filesystem isolation, seccomp syscall filtering, and credential injection — all at the process level inside the pod.

Inference plane

Three-tier routing: security (where may the query go?), cost (which model?), efficiency (which replica?). NIM, TensorRT-LLM, and vLLM serve tokens on any accelerator. Guardrails screen inputs and outputs at the inference boundary.

Skills & MCP Gateway

Skills are thin clients — definitions and API bindings, not GPU workloads. All tool calls leave the pod through the MCP Gateway, authorized by SVID token claims, never by prompt content. Backends sit behind neutral REST/MCP interfaces.

Defense in Depth: Three Isolation Rings

Each ring assumes the ring inside it has already been compromised. Four cross-cutting controls apply across all three. The rings limit what a compromised agent can do; the controls reduce the chance it gets compromised and remove the rewards if it does.

Ring 1 — Process

OpenShell supervisor enforces per-binary, per-path, per-endpoint policy via seccomp, Landlock, and network namespaces. The agent cannot override this because the policy lives outside the process it constrains. Irreversible after process start.

Ring 2 — Pod

Kubernetes pod security standards, SELinux, NetworkPolicy, and resource quotas bound what the pod can reach. Optionally, Kata Containers add a dedicated microVM kernel per sandbox pod.

Ring 3 — Hardware

Confidential containers extend the trust boundary into silicon. AMD SEV-SNP and Intel TDX protect agent memory at runtime even from the host node. Hardware attestation verifies the sandbox runs the code it claims before secrets are released.

Inference Routing & Skill Placement

An inference request crosses three routers because the three decisions have different owners: where (security), which model (cost), and which replica (efficiency). Skills follow three execution patterns — only one runs in the pod.

Tier 1 — Security

Lives client-side in every sandbox, inside the supervisor. Confidential context never leaves the cluster. Anything routed externally is PII-masked first. Masking is detection-and-redaction — monitor for false negatives.

Tier 2 — Cost

A lightweight classifier selects the cheapest model that can handle the request. Adds latency and can misroute — needs a fallback that escalates on low confidence. This tier is a measured trade-off.

Tier 3 — Efficiency

Once the model pool is fixed, llm-d endpoint picker maximizes KV-cache hits and balances load across vLLM workers. Prefill/decode disaggregation further optimizes throughput under concurrency.

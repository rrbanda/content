Part 1

How it works

Exploiting the natural randomness in LLM sampling. The Gumbel-max trick gives us distortion-free watermarking.

Confidential: Red Hat associate and NDA partner use only. No further distribution
The Idea

The Gumbel-max trick: keyed noise on log-probabilities

  • Ordinary sampling: add fresh Gumbel noise to each candidate's logits, take the argmax — this is how Model Runner V2 already works
  • Watermarked sampling: replace fresh noise with keyed noise from a PRF seeded by the secret key, the last context_width tokens, and each candidate token ID
  • Same inputs → same noise → a detector with the key can replay every draw
  • Distortion-free guarantee: in expectation over keys, p(token i) remains exactly the model probability

The PRF is Philox4x32-10 (counter-based, not cryptographic). It generates 4 values per invocation, so the fused GPU kernel processes 4 consecutive candidate token IDs together. Context width defaults to 4.

Confidential: Red Hat associate and NDA partner use only. No further distribution
Inside vLLM

Only the final sampling step changes

  • Model scores (logits) → computed normally
  • Penalties, constraints, structured output grammars → applied normally
  • Temperature, min-p, top-k, top-p → applied normally
  • GPUWatermarkSampler invokes the algorithm-specific Watermarker for the final stochastic pick
  • A fused Triton kernel handles Philox PRF generation, Gumbel transformation, and argmax in one GPU pass — no CPU transfer
  • Per-row mask lets the same kernel handle watermarked and unwatermarked requests in one batch

Example · Step 1 of 2

Each candidate gets keyed Gumbel noise

  • Context: the cat sat on ?
  • PRF(key, context, candidate_id) → uniform value → Gumbel transform → added to logit
  • The candidate with highest logit + Gumbel noise wins
  • Including the token ID means every candidate gets different noise; including the context means noise changes at each generation step

Illustrative values. Context = last 4 tokens (vLLM default). Including the candidate token ID in the PRF input is what makes this a per-token watermark, not just a per-position one.

Example · Step 2 of 2

The window slides, the noise changes

  • Context slides: cat sat on my ?
  • New context → new PRF values → completely different noise for every candidate
  • Rerunning with the same key reproduces it exactly — this is what makes detection possible
  • The signal is in which tokens were chosen, not in any attached metadata — copy-paste preserves it

Larger context_width values make the watermark less robust to edits: one insertion changes more subsequent contexts. Values above 16 emit a warning.

Detection

Detection replays the PRF, not the model

  • For each token t, the detector recomputes PRF(key, context, t) using the preceding tokens
  • Transforms the value into a per-token score; for unwatermarked text these scores are Exp(1)
  • Sums the scores → under H₀ (no watermark), the sum follows a Gamma(n, 1) distribution
  • One-sided p-value: probability that unwatermarked text produces a score this high
  • No model weights, no GPU: detection runs on CPU from token IDs alone

Repeated contexts are scored once by default (deduplicate_contexts=True in detector) so identical PRF vectors are not treated as independent evidence. Scores and p-values expose signal info — keep detection behind access control.

Performance

Near-zero throughput impact — measured on H100

  • Qwen3.5-27B + MTP-3, one H100, 512 output tokens, 8 keys × 9 batch sizes
  • Mean throughput change across batch sizes: −1.1% to +2.0%
  • Batch 1: 113.9 tok/s unwatermarked vs 113.9 watermarked (−0.23%)
  • Batch 256: 1590.7 vs 1586.5 (−0.58%)
  • Context deduplication overhead: ≤ 0.19% (Qwen3.5-27B)
  • The fused kernel avoids materializing a [batch × vocab] noise tensor — PRF, Gumbel, and argmax are one pass

From the vLLM blog (Sep 24, 2026) by Rialland (Mistral), Veitner & Ruiz (Red Hat). Medians across 8 watermarked keys, 4 unwatermarked controls.

Part 2

Speculative decoding

A small drafter guesses ahead, the big model checks. Both kinds of tokens need a watermark.

Confidential: Red Hat associate and NDA partner use only. No further distribution
Speculative Decoding

One round: guess, check, keep

  • Step 1: Drafter proposes k tokens (e.g. 3 with MTP)
  • Step 2: Target model checks all k in one forward pass using probability-ratio test: accept if r < min(1, p(x)/q(x))
  • Step 3: Rejected → sample from residual distribution; all accepted → bonus token from target
  • Applying the same watermark key to both models can reduce their overlap and lower acceptance rate
  • Solution: dual-key watermarking (PR #56122), based on SynthID-Text Algorithm 6

Supported draft methods: MTP, EAGLE, EAGLE3, DSpark. DFlash support is pending (issue #59662). ngram and separate draft_model are rejected at startup.

Speculative Decoding

Two approaches to watermarking speculative decoding

Target-only
  • gumbel + allow_target_only
  • sat on my
  • Accepted drafts carry no watermark
  • Signal diluted by acceptance rate
  • p = 2.1e-31
Dual-key (recommended)
  • dual_key_gumbel
  • sat on my
  • Drafts → key A; recovery/bonus → key B
  • Every token carries signal
  • p = 5.0e-56

Dual-Key Protocol

The dual-key protocol preserves acceptance rate exactly

  • Keys A and B are derived from one configured master key
  • Draft tokens sampled from qwm(·; key A) — the drafter's watermarked distribution
  • Accept/reject uses unwatermarked probabilities: r < min(1, p(x)/q(x)) — identical test to no watermark
  • Rejected → sample from residual(p, q)(·; key B); all accepted → bonus from pwm(·; key B)
  • Acceptance rate is unchanged because the ratio test never sees watermarked probabilities
Key A (drafter) Key B (target)

Implements SynthID-Text Supplementary Algorithm 6. The alpha config parameter has no effect under speculative decoding; the protocol selects the key. See section K.13 of SynthID-Text supplementary for non-distortion proof.

Detection Tuning

The detector's alpha weights the two keys

  • Config alpha (default 0.1): in non-spec-decode mode, probability of using key B per token — ignored under spec decode
  • Detector alpha: weight given to key B scores (default 0.2 in vLLM)
  • Under spec decode, key B's share ≈ 1/(1 + k × acceptance) where k = draft tokens per step
  • Prose: 1/(1 + 3 × 0.34) ≈ 0.49 → use alpha ≈ 0.5
  • JSON: 1/(1 + 3 × 0.91) ≈ 0.27 → alpha ≈ 0.2
  • The best alpha is key-dependent and template-dependent — compare on your own data

With 8 keys on JSON: alpha 0.2 detected clearly more for keys 0, 7, 42; alpha 0.5 detected more for key 99. Without key 42, the two were roughly equal after FPR matching.

Part 3

Repeated contexts

The same context always gives the same noise. Without mitigation, this creates repetition loops.

Confidential: Red Hat associate and NDA partner use only. No further distribution
Repeated Contexts

Same context, same noise — biased toward loops

  • A fixed key + repeated context → identical PRF values → same token favored again
  • Example: 1 + 1 + 1 + 1 + ...
  • Context (1, +, 1, +) repeats → same noise → infinite loop in the worst case
  • Even without complete loops: lower diversity, longer generations, reduced quality
  • This is the gap between single-token non-distortion and single-sequence non-distortion
Confidential: Red Hat associate and NDA partner use only. No further distribution
Repeated Contexts

Context deduplication: plain pick at repeated contexts

  • When the last context_width tokens already appeared earlier, vLLM uses ordinary sampling
  • the keeper lit the lamp ... the keeper lit the stove
  • The detector independently deduplicates — skips repeated contexts — so no evidence is lost
  • This gives single-sequence non-distortion (section G.3 of SynthID-Text supplementary)
  • Overhead: ≤ 0.19% throughput reduction on Qwen3.5-27B

On by default: deduplicate_contexts = "single_turn". Search window defaults to last 8,192 positions. Values below 1,024 emit a warning.

In Production

Prometheus monitoring and stability guarantees

  • vllm:watermark_requests_total counts finished requests by status:
  • watermarked — sampled with watermark on
  • skipped — wanted watermark but couldn't (e.g. temperature=0)
  • not_watermarked — explicit opt-out, beam search, pooling
  • Sum over status = vllm:request_success_total on the same instance
  • Forward compatibility: golden tests store reference token picks and detector scores per algorithm. A change that alters them fails the vLLM test suite. PRF input mapping is versioned.

Counter exists only with --watermark-config. Status is per request, not per token. In disaggregated prefill/decode, sum over decode instances only.

In Production

Operating checklist

Key
Keep the key secret. Anyone with it can detect, forge, or strip the watermark.
Access
Detection behind access control. Repeated queries can reveal or erase the signal.
Match
Same tokenizer, algorithm, key, context width, and PRF for detection.
Measure
Check false positives on your own unwatermarked traffic with your deployed key.

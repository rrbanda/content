Motivation

Why watermark generated text

Regulation
Transparency rules such as the EU AI Act (Art. 50) and California SB 942 ask for machine-detectable marking of AI-generated text
Provenance
Check later whether a piece of text came from your deployment
Invisible
No metadata to strip. The signal is in which tokens were chosen, and readers cannot see it

Part 1

How it works

A model picks each token by rolling dice. A watermark swaps in dice that only the key holder can replay.

Confidential: Red Hat associate and NDA partner use only. No further distribution
The Idea

Keyed dice instead of fresh dice

  • The last few tokens and a secret key set the random numbers the sampler uses
  • Last 4 tokens (context): the old light house  + secret key
  • Keyed random function: same inputs → same numbers
  • Per candidate: keeper 0.91   was 0.12   stood 0.47  …
  • Pick: keeper (highest keyed value wins)

Inside vLLM

Only the final pick changes

  • Everything before the last sampling step runs exactly as without a watermark
  • Model scores (logits) → penalties and constraints → temperature, top-k, top-p
  • Watermark off: random draw
  • Watermark on: keyed draw

Watermarking runs in vLLM's Model Runner V2 sampler

Each candidate gets keyed noise

  • The candidate with the highest preference + noise wins. Here the noise lifts “my” to the top.

  • Model preference + keyed noise → combined scores for: the, a, my, her, mat

Example · Step 2 of 2

The window slides, the noise changes

  • Each token gets fresh noise from its own context. Rerunning with the same key reproduces it exactly.
  • Context slides one token: cat sat on my ?
  • New context → new noise → different candidates favored
  • model preference + keyed noise → mat, bed, lap, desk, rug

Detection

Detection replays the dice

  • With the key, the detector recomputes each chosen token’s number
  • Above 0.9: 51% of watermarked tokens, 12% of ordinary ones
  • Unwatermarked text: values spread evenly across 0–1
  • Watermarked text: values piled up near 1

Measured: two 200-token stories from Qwen3.5-0.8B, one per row, one dot per token

Configuration

One engine flag, one request field

Engine: set once at startup

Every request is watermarked by default.

vllm serve MODEL \ --watermark-config \ '{"algorithm":"gumbel", "key":42}'
Request: opt out

For internal or non-user-facing traffic. Restrict this field to trusted callers.

{"model": "MODEL", "messages": [...], "watermarking": false}

Greedy requests (temperature 0) cannot be watermarked and skip it with a warning

Part 2

Speculative decoding

A small drafter guesses ahead, the big model checks. Both kinds of tokens need a watermark.

Confidential: Red Hat associate and NDA partner use only. No further distribution
Speculative Decoding

One round: guess, check, keep

Up to four tokens per big-model pass instead of one. The output follows the big model’s distribution.

  • 1 · drafter guesses 3 tokens: sat on the
  • 2 · big model checks all 3 in one pass, adds one:
  • sat kept   on kept   the rejected   my added

Speculative Decoding

Two ways to watermark it

Target-only
  • gumbel + allow_target_only_watermarking
  • sat on my
  • Accepted drafts carry no watermark, so the signal thins out as acceptance rises
  • story p = 2.1e-31 · 93/128 answers flagged
Dual-key
  • dual_key_gumbel
  • sat on my
  • Drafts carry key A, the big model’s own tokens carry key B. Every token carries signal.
  • story p = 5.0e-56 · 114/128 answers flagged
Measured: Qwen3.5-0.8B with its MTP draft head, 3 draft tokens; 200-token story and 128 GSM8K answers

Part 3

Repeated contexts

The same context always gives the same noise. vLLM makes sure that does not snowball.

Confidential: Red Hat associate and NDA partner use only. No further distribution
Repeated Contexts

Same context, same noise

Without a fix, a repeated phrase gets the same push every time, which feeds repetition.

  • the keeper lit the lamp … the keeper lit the lamp
  • Same context → same noise → pushed toward the same token again → loops

Illustrative tokens · context = last 4 tokens

Confidential: Red Hat associate and NDA partner use only. No further distribution
Repeated Contexts

A repeated context gets a plain pick

vLLM samples normally when the last 4 tokens already appeared earlier in the output.

  • the keeper lit the lamp … the keeper lit the stove
  • watermarked, scored by detector     plain pick, skipped by detector
  • The detector skips repeated contexts anyway, so the watermark loses no evidence

On by default (deduplicate_contexts = "single_turn")

Confidential: Red Hat associate and NDA partner use only. No further distribution

Repeated Contexts

The same rule in speculative decoding

A draft, replacement or bonus token at a repeated context is a plain pick. Contexts inside the drafted block count too.

  • drafter proposes: the key A   keeper plain   lit key A
Key A (drafter)
Key B (big model)
Plain pick at a repeated context
  • Keep or reject still uses the same test, so the speed-up is unchanged

Measured with MTP, 128 GSM8K answers: repeated contexts 19.6% without dedup, 17.1% with, 17.6% unwatermarked

In Production

Text watermarked today stays detectable

Generation and detection are a contract. vLLM tests it on every change.

  • Generated today → watermarked → next release → still detected → release after → still detected
  • Golden tests store reference token picks and detector scores for each algorithm setting
  • A change that would alter them fails vLLM’s test suite

PR #56809 · the PRF input mapping is versioned

In Production

Operating checklist

Key
Keep the key secret. Anyone with it can detect, and can also forge or strip the watermark.
Access
Keep detection behind access control. Scores leak information about the signal.
Match
Use the same tokenizer, algorithm, key and context width for detection.
Measure
Check false positives on your own unwatermarked traffic, especially templated output like JSON.
